# 25 看图缓存、预取与胶片条（IMGCACHE）

分支 `perf/image-cache`。目标：看图翻页不卡、缓存命中高、提前缓存；底部按需加载的小图列表。

## 卡顿的根因（改前）

1. **每次翻页同步全尺寸解码**：空格预览 `buildPreview → decodeImage` 读整个文件、`image.Decode` 全分辨率（24MP 约 0.8 s），再缩到 2048 px；没有解码结果缓存，也没有预取，翻回上一张照样重解。
2. **EXIF 方向未应用**：`decodeBytesScaled` 用 stdlib 解码，竖拍照片横着显示（mygo 的 `DecodeBitmap` 会转，但它不缩放，项目没用它）。
3. **缩略图缓存**：键只有路径（文件改了不更新）；LRU 的 `touchThumbKey` 每帧每格线性扫描最多 2000 个键（UI 线程上 O(n)）；64 MB 预算在 300 张 128 px 带 mip 时偏紧；没有磁盘缓存，每次启动重解。
4. **网页**：网格缩略图和预览都直接下**原图**（`/d/…` 无缩放），手机上一张 24MP JPEG 4–8 MB；无 Cache-Control；每翻一张还多一次 `/api/fs/get` 往返；没有预取。

## 改动

| 位置 | 做法 |
|---|---|
| `imgcache.go` | 屏幕尺寸（2048 px）解码图单独的字节预算 LRU（128 MB，键 = 路径+大小+mtime+边长）；同一张正在解码时后来者等待而不重复解码；2 个后台 worker 预取**翻页方向后 2 张 + 反方向 1 张**，换位置时丢弃排队中的旧任务。预览开着（窗格或空格预览）且选中图片时触发。 |
| `thumbdisk.go` | 磁盘缓存 `UserCacheDir/sunvale/thumbs`：键 sha1(路径\|大小\|mtime\|边长)，不透明存 JPEG q85、带透明存 PNG；上限 1 GiB，每 128 次写入检查，按 mtime 删到 80%；读命中会刷新 mtime。缩略图、相册、屏幕图、网页缩小版共用。 |
| `imgexif.go` / `imgsize.go` | 先缩小再按 EXIF 方向旋转（只在小图上转）。 |
| `thumb.go` | LRU 改 `container/list`（O(1) touch）；预算 128 MB；`mediaThumbFor` 用列表的 mtime 判断过期；`peekThumb` 给预览当低清占位。 |
| `quicklook.go` / `imageview.go` | 预览未解完时先把缓存里的缩略图拉伸显示（低清占位 → 清晰图）；深色看图底。 |
| `imagestrip.go` | 底部胶片条：44 px 方块，当前高亮并居中，点击跳转；**只画/只解码放得下的那一段**。 |
| `remote_rendition.go` / `remote_dl.go` | `/d/…?w=N`：取整到 256/512/1024/1600/2048/3072 档，服务端缩放并存磁盘缓存；强 ETag（mtime-size-wN）、`Cache-Control: private, max-age=604800`、`inline`；最多 3 张并发解码；>64 MB 或比最大档大则发原图。不带 `w` 的下载不变。 |
| 网页 `remote_manage_web.html` / `remote_web.html` / `internal/remote/webstrip.go` | 网格缩略图用 `w=256`；预览先放 256 px（已缓存）再换屏幕尺寸版（屏幕长边×DPR）；放大到 1.5× 才取原图；翻页用 `new Image()` 预取方向上 2 张 + 反向 1 张；有签名的图片不再调 `/api/fs/get`；底部胶片条（IntersectionObserver 懒加载，横向滑动）+「第几张 / 共几张」。手机 toast 在预览打开时上移，不压胶片条；↑存/↓撤 按钮和键不变。 |

## 测量

环境：box，8 核 CPU、无 GPU，隔离 HOME/XDG。测试集 300 张：6 张 6000×4000 JPEG、37 张 4000×3000、其余 1920–3520 px；30 张 PNG、10 张 WebP；共 461 MB。翻页模拟：每 150 ms 按一次「下一张」（快速连翻），共 79 步。网页：headless Chrome，手机限速 20 Mbps / 40 ms RTT，每 600 ms 翻一张。

| 指标 | 改前 | 改后（首次，冷） | 改后（磁盘缓存热） |
|---|---|---|---|
| 原生翻页出图 p50 | 286 ms | 104 ms（仅内存）/ 0.02 ms（磁盘缓存开启的首轮） | 0.02 ms |
| 原生翻页出图 p95 / max | 604 / 941 ms | 493 / 683 ms（仅内存）· 225 / 664 ms | 0.025 / 34 ms |
| 预览缓存命中（翻页那张已在缓存或正在预取） | 0/79 | 78/79 | 78/79 |
| 单张解码 2048 px（p50 / 24MP） | 275 ms / 823 ms | 同（解码本身未变快） | 31 ms / 27 ms（读磁盘缓存） |
| 网格首屏 40 张缩略图全部出现 | 989 ms | ≈ 同 | 174 ms |
| 快速滚动后回看缩略图首帧命中 | 404/560 | 405–470/560 | 560/560 |
| UI 线程每帧缩略图查表 max | 12.0 ms | 2.5 ms | 0.36 ms |
| 翻页后存活堆（GC 后） | 3 MB | 221 MB（内存 LRU，按预算） | 187 MB |
| 翻页期间堆峰值 | 477 MB | 763 MB | 409 MB |
| 网页 手机 下一张出清晰图 | 384–2331 ms（下原图 0.6–4 MB） | 16–30 ms，偶发 188 ms | — |
| 网页 桌面 下一张出清晰图 | 281–2367 ms | 8–19 ms | — |
| 网页 24MP 一张的传输量 | 4.09 MB | 2048 版 178 KB，缩略图 4.9 KB | — |

说明：
- 「帧卡顿」在无 GPU 的 box 上没法测真实帧时间，用 UI 线程上的缩略图查表耗时代替；解码一直在后台 goroutine，没有进 UI 线程。
- 堆峰值升高是有意的：用内存换翻页速度，屏幕图 LRU 有 128 MB 预算（mygo 位图另存半尺寸副本，实际约 1.5 倍）。
- Go 标准库的 JPEG 解码不支持 DCT 缩放（libjpeg 的 1/2、1/4、1/8 解码），go.mod 里也没有可用的库，所以单张冷解码时间没变；靠预取和磁盘缓存把它挪出翻页路径。
- 服务端 24MP 冷缩放约 0.9 s，被客户端预取提前触发；结果进磁盘缓存后 <1 ms。
